# herdr compatibility observations

Consult this reference for RPC framing, protocol negotiation, subscription
recovery, Agent launch/input, terminal attach, or remote scrolling behavior.
These observations were moved from `CLAUDE.md` without changing their evidence
versions. They are historical evidence, not fresh tests on the installed herdr.

## Current routing

- Unix API and Events use direct-streamlocal; Unix terminals use PTY exec
  ([ADR 0011](../adr/0011-libssh2-direct-streamlocal-transport.md)). Native
  Windows uses `remote-api-bridge` and `terminal session control`
  ([ADR 0018](../adr/0018-native-windows-hosts.md)); Unix forwarding refusal
  never selects the Windows path.
- Start with [HeelerSSHTransport](../../Sources/Heeler/Transport/HeelerSSHTransport.swift)
  and [EventsSession](../../Sources/Heeler/Transport/EventsSession.swift) for
  current adapters and recovery. Older symbol names below belong to their
  observation's version; use the [source map](navigation.md) to reach current owners.
- The committed schema is [scripts/herdr-schema.json](../../scripts/herdr-schema.json).
  Generated types describe that snapshot, not every method in every herdr release.
- For native Windows setup or runtime acceptance, use the
  [setup guide](../guides/windows-setup.md) or
  [acceptance checklist](../guides/native-windows-testing.md).

## Versioned observations

Rediscovering these is expensive. Each fact retains its evidence version and method (live observation or source review); older observations are not re-tests on a newer release. For 0.9.0 subscription ordering, compatibility evidence, and remaining verification, read [the integration review](../research/herdr-0.9.0-compatibility.md).

- The herdr API socket serves **one request per connection** (read one line, write one line, close). Only `events.subscribe` keeps the connection open. Plan channel usage accordingly. (Re-verified live on 0.8.0: a second write on a served connection gets `EPIPE`. `pane.graphics.stream`, previously listed here, does not exist in the 0.8.0 schema — graphics methods are `pane.graphics.set`/`clear`/`info`, all one-shot. 0.9.0 and 0.9.1 accepted `pane.graphics.stream` although their schemas omit it, and kept its connection open for image frames; 0.9.2 removed the graphics API, so all four methods answer `unknown_method`: source review at `v0.9.0`, `v0.9.1`, `v0.9.2` and `v0.9.4`, and the 0.9.2 release notes.) Since 0.9.2, `server.ssh_agent.register` also holds its connection on Unix: herdr answers `ok`, then keeps the connection open until the client closes or writes to it, or the server stops (source review of `src/api/server.rs` at `v0.9.2`; live on isolated 0.9.3 and 0.9.4 backends, still open 2 s after the reply). Heeler does not call it.
- Wire format: request `{"id": "<any string>", "method": "...", "params": {...}}` + `\n`; `params` is required, and `{}` satisfies it. Success `{"id", "result"}`, failure `{"id", "error": {"code", "message"}}` (both re-verified live on 0.8.0), subscription event lines `{"event", "data"}` with no id.
- The first message on any new connection path should be `ping` — it returns the server protocol version (0.8.2 answers `{"version":"0.8.2","protocol":20,...}`; 0.8.0, verified live, answered `{"version":"0.8.0","protocol":19,...}`). herdr's API has no stability guarantee; parse leniently (ignore unknown fields). The app enforces a **floor**, not equality: `HeelerSSHTransport.minimumProtocolVersion` refuses older servers, `generatedProtocolVersion` only drives an advisory notice. Equality here made every 0.8.0 Host unusable (#140) — do not restore it.
- The API schema is exported offline via `herdr api schema --json` (JSON Schema 2020-12): the binary prints the schema built into it and contacts no server, while a bare `herdr api schema` prints only a summary (source review of `src/cli/api.rs` at `v0.9.4`). Its `$ref` paths are non-standard nested (`#/schemas/request/$defs/X`) — preprocess before feeding codegen tools. The committed snapshot is the 0.9.4 export (protocol 22), byte-identical to 0.9.3's. It declares 102 request methods, as 0.9.0's did, but not the same ones: 0.9.1 added `pane.link.resolve`, and 0.9.2 added `pane.clear` and `server.ssh_agent.register` and removed `pane.graphics.set`/`clear`/`info` (diffed against the 0.9.0 snapshot; versions from source review of `src/api/schema.rs` at `v0.9.0`, `v0.9.1` and `v0.9.2`). It declares 26 event kinds, and every one of those kinds has a typed `EventData` variant; separately, 3 pane-scoped kinds (`pane.output_matched`, `pane.agent_status_changed`, `pane.scroll_changed`) have typed `SubscriptionEventData`. The event kinds, their `EventData` variants and the subscription-event schema are unchanged from 0.8.2, but the event schema's `PaneInfo` gained an optional `restore_error` in 0.9.2 (diffed against the 0.8.2 and 0.9.0 snapshots; the version from source review at `v0.9.1` and `v0.9.2`). Payloads herdr actually emits are still worth verifying empirically.
- Pane ids are opaque strings. Protocol-22 `scripts/herdr-schema.json` declares `pane_id` as a string with no `pattern`. Observed herdr 0.7.5 captures (`w1:pA`, `w3:pB`, `wV:p1`) and live 0.8.0 `agent.list` samples (`w1:pT`, `w1C:p1`, `wR:pC`, `wV:p1H`) are alphanumeric `w…:p…` identifiers and include uppercase letters. Those captures contain no tmux-style `%N`; that does not prove herdr can never emit it. Treat every pane id as an opaque string; do not parse or validate a grammar.
- SSH exec channels are session channels, capped by sshd's `MaxSessions` (default 10) per connection. All RPC traffic must go through a request queue that bounds concurrency.
- `herdr agent attach` requires a TTY (ratatui). It works over an exec channel only when a PTY is requested.
- herdr 0.7.5 tightened `agent.start` (verified against a live 0.7.5 server): the kind must be on its supported-agent list (arbitrary commands like `bash -i` are rejected with `unsupported interactive agent kind`), and a freshly created pane is rejected with `agent_pane_busy` ("not an available shell") until its shell reaches the interactive prompt, a few seconds. On 0.8.0 and later the start is asynchronous: an accepted start returns `launch_pending: true` at once (verified live on 0.8.0, 6ms after pane creation). herdr still answers `agent_pane_busy` while a startup command holds the fresh pane's foreground, so the retry is required, not 0.7.5 compat: live on 0.9.3, a zsh whose rc runs `/bin/sleep 1` was refused until about 1.2 s (spec #449's verification rounds; their output was not saved), and live on 0.9.4, fish with Homebrew vendor configuration drew 146 `agent_pane_busy` and 2 canonical refusals before its launch went through at about 2.4 s (probed every 10 ms). On a macOS Host, 0.9.4 also refuses a launch line longer than the terminal's canonical input limit (1,024 bytes) until the shell's line editor starts, with `agent_start_input_failed` and "input contains a N-byte line but the terminal is in canonical mode with a 1024-byte limit; wait for the shell prompt and retry", where N is the UTF-8 length of the shell-quoted command line plus Enter (verified live on 0.9.4 with a 1,100-character ASCII argument and a CJK one). The refusal reserves no name and queues no input (live, and the v0.9.4 source checks before either), so resending the same request is safe. Live on 0.9.4, such a launch went through within about 0.1 s in bash, a bare zsh, ksh and tcsh, after about 2.4 s in fish, and never in dash, even at its prompt. Linux and Windows Hosts never refuse, and herdr's other `agent_start_input_failed` messages ("could not determine canonical input capacity", "pty actor closed", OS errors, "no available capacity", "channel closed") are not about readiness (v0.9.4 source review). herdr 0.9.3 accepted the same long launch, cut it to 1,024 bytes and never ran it (spec #449's verification rounds; their output was not saved), which Heeler cannot detect. `HeelerSSHTransport.isShellReadinessRefusal` matches only the busy and canonical refusals, and the private `HeelerSSHTransport.startAgentAwaitingShell` resends the same request on either within one 10 s budget at a 500 ms pace; any other refusal fails at once.
- Default remote socket: `~/.config/herdr/herdr.sock` (still the path a live 0.8.0 server serves); named sessions live under `~/.config/herdr/sessions/<name>/herdr.sock` (not re-tested on 0.8.0). Resolve `$HOME` over exec once per host.
- If the herdr server is not running, connecting to the socket fails outright; there is no auto-start on the socket path. Fallback: run a herdr CLI command over exec (verify auto-spawn behavior — open question).
- `herdr agent attach` resolves its target against **agents only**: attaching a plain shell pane fails with `agent_not_found` (verified against a live 0.7.5 server; resolution unchanged in the 0.8.2 source). Ordinary terminals attach with `herdr terminal attach <terminal_id> [--takeover]` instead (0.8.2, verified against the installed CLI and the `v0.8.2` source tag): after resolving the Agent's `terminal_id`, `agent attach` enters this exact same client path (`src/cli/agent.rs` → `run_terminal_attach`). It targets a **terminal id** (from e.g. `tab.create`'s root pane), speaks the client socket derived from `HERDR_SOCKET_PATH` by inserting `-client` before `.sock` — distinct from both the JSON API socket and `remote-client-bridge` — supports raw input, resize, and takeover, allows **one writable attach owner per terminal** (a second attach without `--takeover` is refused; takeover displaces the previous owner), and is Unix-only in the inspected source (`#[cfg(unix)]`). Run it over exec with a PTY, as with `agent attach` — the 0.8.2 client puts the real terminal into raw mode. Interacting with a shell pane over the JSON API still means `pane.send_text`/`pane.send_keys` plus `pane.read`. Note `pane_output_changed` is emitted but **not subscribable** (0.8.0: the one emitted kind missing from the `Subscription` oneOf), so there is no output-change push — see the read/refresh facts below.
- herdr 0.9.4's direct attach (`agent attach` and `terminal attach`) sets the terminal up **before** its handshake, and that setup now probes the host terminal: after entering the alternate screen it writes `ESC[?1016$p ESC[c` (a DECRQM for SGR pixel mouse, then DA1) and waits up to 250 ms for the answer; herdr's own client shell sends `ESC[?1016$p ESC[?u ESC[c`, which also asks for the kitty keyboard flags. An answer that arrives later reaches the Pane as typed input, so Heeler's Unix attach pump drops the probe (#451); the native Windows `terminal session control` handshakes without any terminal setup and never writes it. Source review of `src/client/terminal_setup.rs` (`query_host_capabilities`) and `src/client/mod.rs` (`run_client_with_mode`) at `v0.9.3` and `v0.9.4`, and of `src/client/terminal_sessions.rs` at `v0.9.4`; live through Heeler's attach command against isolated 0.9.3 and 0.9.4 servers, 0.9.4 wrote the probe 138 bytes after the bootstrap marker and 0.9.3 wrote none, and a stand-in terminal that answered 400 ms late, or at once behind a proxy adding 400 ms of round trip, had its answer typed into the Pane. With setup first, a handshake failure arrives wrapped in the setup and its restore (alternate screen on, probe, alternate screen off) ahead of herdr's `Error: ...` line, while a socket connect failure returns before terminal setup and carries neither (live on 0.9.4, against a stand-in client socket that closes during the handshake and with no client socket at all); 0.9.3 handshakes first, so neither failure is wrapped. Since 0.9.2 herdr re-queries the host theme on resize, but only when `attach_escape` is unset, which excludes direct attach, so a direct attach writes no host query on resize (source review of `src/client/mod.rs` at `v0.9.1` through `v0.9.4`).
- `pane.send_text` types into any pane's PTY; a trailing `\n` presses Enter and the shell executes the line (verified live). `tab.create`/`workspace.create` accept `cwd`, `env`, and `label`, and `workspace.create` already returns a root pane running the user's shell — a plain terminal pane needs no `agent.start`.
- Reading pane content, verified live on 0.8.0: `pane.read`/`agent.read` take `source: visible|recent|recent_unwrapped` plus `lines` — **no offset or cursor**, so remote history is not addressable. `recent` defaults to 80 lines; the server caps every read at **1000 lines**. For alternate-screen TUIs (claude), history is capturable **only while the agent is idle**: `agent.read` fails `agent_not_idle` while working, and `pane.read` silently degrades to the visible screen while reporting `truncated: false` — use `agent.read` whenever depth matters. `read.revision` is always 0, never a change signal. The text lives at `result.read.text` (nested), not top-level.
- Output-change signals, verified live on 0.8.0: `pane.output_matched` is edge-triggered — one push when the visible buffer's match predicate flips no-match→match (plus one at subscribe time if already matching), silence during sustained output — useless as a change feed. `pane.agent_status_changed` is the precise push signal (two ~125-byte events per prompt round trip). `pane.updated` remains a ~4/s noise source. `events.wait` implements only pane agent-status matches despite the schema declaring 19 `EventMatch` variants, and its param is `match_event` (a single object).
- `agent.prompt`, verified live on 0.8.0: types the text **and Enter** (auto-submits); without `wait` it returns `agent_prompted` immediately — a delivery ack, nothing more. `wait.until` must include `done`: claude finishes on `done`, not `idle`, so idle-only waits reliably time out. Prompting a **working** agent is accepted unconditionally; queueing happens inside the agent TUI (verified for claude), not in herdr. `target` accepts pane ids and agent names, not agent-session UUIDs.
- `pane.send_input {pane_id, text?, keys?}` (verified live on 0.8.0) inserts without submitting when `keys` is omitted; `{text, keys: ["enter"]}` is an atomic type-and-submit. Key-name parsing is shared with `send_keys` and laxer than 0.7.4: `enter`/`esc`/`ctrl+c`/`C-c` accepted case-insensitively, `ctrl-c` still rejected with `invalid_key`.
- Malformed requests are answered with `id: ""` instead of the request id (verified live on 0.8.0) — id-keyed response matching needs a fallback or such requests pend forever. Since 0.9.2 (herdr 241063f7), a malformed request whose line is a JSON object with a string `id` gets that id back, while invalid JSON, a non-string `id` and duplicate `id` keys still get `""` (source review of `src/api/server.rs` at `v0.9.1` and `v0.9.2`; live on isolated 0.9.3 and 0.9.4 backends with an unknown method, a missing `params`, invalid JSON, a numeric `id` and duplicate `id` keys), so the wire layer's empty-id fallback stays. `ping` on 0.8.0 also reports `capabilities` (`live_handoff`, `detached_server_daemon`); 0.9.2 added `ssh_agent_registration` (source review), which isolated 0.9.3 and 0.9.4 backends on macOS reported live as `true`.
- Starting claude in a cwd absent from `~/.claude.json` blocks on an in-TUI trust dialog herdr cannot dismiss (hit live on 0.8.0) — a fresh-directory agent launch can wedge before its first prompt.
- Rename methods, verified against a live 0.7.5 server: `agent.rename` enforces `^[a-z][a-z0-9_-]{0,31}$` (`invalid_agent_name` otherwise) and clears the custom name when `name` is null or omitted; `workspace.rename` accepts **any** label (empty, whitespace, 500 chars). The `pane_updated` event a rename fires does **not** carry the agent name, and `pane.updated` fires on every terminal-title change (34 events in 6s measured live) — do not use it as a resync trigger; renames surface via post-RPC resync instead.
- `worktree.remove` refusals (source review of `is_dirty_worktree_remove_error` in `src/worktree.rs` and `handle_api_worktree_remove_finished` at v0.9.0, v0.9.1 and v0.9.4; live on an isolated 0.9.4 server whose git was 2.54.0, Apple Git-157): an unforced removal that git refuses answers `dirty_worktree_requires_force` when herdr recognizes git's message, ignoring case, and `worktree_remove_failed` otherwise. Through 0.9.0 only "'<checkout path>' contains modified or untracked files, use --force to delete it" is recognized. Since 0.9.1 (aff99878, #4238) herdr also recognizes "fatal: working trees containing submodules cannot be moved or removed" and runs git with `LC_ALL=C`, so the text is English whatever the Host's locale; on 0.9.0 the submodule refusal arrives as `worktree_remove_failed`. git refuses a Worktree with an initialized submodule before it looks for changes, so this refusal says nothing about whether the checkout is clean: live, a clean Worktree with an initialized submodule and the same Worktree with an untracked file both got the submodule message, and on a default-session server `herdr worktree remove --workspace <id> --force` over SSH exec removed it. With only a `work` session running, that bare command failed with `server_not_running` and `herdr --session work worktree remove --workspace <id> --force` succeeded. On Windows, herdr 0.9.4 looks for changes itself before running git (source review only), so a Worktree with changes gets the dirty message there. `WorktreeRemovalRefusal` names the submodules, keeps Show Changes and hands over the session-scoped forced command.
- Restored Worktrees, herdr 0.9.4 (source review of `refresh_restored_workspace_git_metadata` and `require_restored_worktree_ready` at v0.9.4; the gate is absent at v0.9.3): a server that restores a saved session at start, or takes over through live handoff, re-reads every restored Worktree's Git metadata in the background. Until that read finishes, `worktree.remove` (checked right after the workspace lookup) and `worktree.create` from that workspace answer `worktree_operation_in_progress` with "Restored worktree is still loading. Try again shortly.", and a read that stalls (a hung network, FUSE or cloud mount) keeps the Worktree waiting. The same code also refuses an operation already running on the checkout ("worktree operation is already in progress for this checkout", present since at least 0.9.0), so `WorktreeRemovalRefusal` shows herdr's own message and Remove Worktree stays available after the alert.
- herdr 0.9.0 lifecycle subscriptions are live-only: await `events.subscribe` acknowledgement before taking `session.snapshot`, consume events during the request, and re-snapshot after reconnect or subscription replacement (verified against the `v0.9.0` source and documentation). Historical observation: 0.7.5 replayed recently buffered events on subscribe; 0.7.4 replayed nothing. Neither is a current recovery guarantee.
- `events.subscribe` is **all-or-nothing**: one pane-scoped entry naming a dead pane fails the entire request with `pane_not_found` (re-verified live on 0.8.0, including alongside a valid global entry; the error id is `<requestID>:sub:<index>:probe`, so it does not correlate with the request id). Since 0.9.2 (herdr 241063f7), setup and probe errors carry the request id instead (source review of `stream_subscriptions` in `src/api/server.rs` at `v0.9.1` and `v0.9.2`; live on isolated 0.9.3 and 0.9.4 backends, a dead pane next to a valid global entry still fails the whole request with `pane_not_found`, now under the request id). The wire layer still surfaces an error whatever its id, which 0.8.0 to 0.9.1 Hosts need. Pane-scoped subscriptions are snapshot-derived and must never outlive the connection they were taken on, or a single exited pane wedges the Host offline forever — see `EventsSession.dropSnapshotSubscriptions`.
- Scrolling an attached terminal's history depends on the **agent CLI**, not on herdr, and the CLI's own history is the only copy. Captured from a pty and from live panes on 0.8.2: `herdr terminal attach` always emits `?1049h` and toggles mouse reporting on then off, leaving whatever the inner application asks for. Claude Code, codex, and grok all set `?1049h` plus `?1000/1002/1003/1006h`, so `TerminalTouchScroll.remoteScrollSequence` sends real SGR wheel reports and all three scroll. Verified live against a Claude pane: six wheel-up reports moved its viewport and made it draw its own `Jump to bottom (click) ↓` affordance. **Measure `claude` in a trusted directory** — in an untrusted cwd it blocks on the trust dialog, emits ~1.2 KB, and sets neither alt screen nor mouse tracking, which reads as a capability difference that does not exist.
- An alternate-screen agent leaves **no herdr-side scrollback**: a live Claude pane reports `max_offset_from_bottom: 0`, and `pane.read`/`agent.read` return only the viewport (49 rows) however many lines are asked for. A plain shell pane on the same server returns 304 of 400 requested. So an app cannot recover an agent's history through the API; the only way back through it is to scroll the CLI itself, and `TerminalScrollControl.canScrollRemoteContent` reports whether that is possible at all.
- `herdr remote-client-bridge` bridges stdin/stdout to the **client socket** (the TUI client/server protocol for `herdr --remote`), not the API socket — verified against herdr 0.7.5 source (`src/remote/unix.rs`, `run_remote_client_bridge`); no API-socket stdio bridge exists in 0.7.5. Its "ensure server running" side effect is why it works as the wake command.
- `plugin.list`, the source of a Host's installed Heeler plugin version (source review of `src/api/schema.rs` and `src/app/api/plugins/mod.rs` `handle_plugin_list` at `v0.7.5`, protocol 17 and the app's floor, so no unknown-method fallback is needed; response shape verified live on 0.9.3): it rereads the plugin registry and manifests from disk on every call, so an update shows without reconnecting; an absent plugin is simply missing from `plugins` (no error); a disabled one is still listed with `enabled: false`; a registry read failure answers `plugin_registry_load_failed`. Each entry carries the manifest `version`, `enabled`, `source.kind` (`github` or `local`; `herdr plugin install` refuses to replace a `local` link) and `warnings`, where `manifest unavailable: …` means herdr kept its last registry entry and the version may be stale. The rest of `InstalledPluginInfo` (manifest arrays, `PopupSize` unions) is outside the wire generator's reach, so `PluginListResult` decodes only those fields by hand. `herdr plugin uninstall <id>` removes GitHub installs and local links alike.
- Plugin hooks and herdr sessions, herdr 0.9.3 (hook environment captured from real hooks of an isolated default, `work`, `herdr` and custom-socket server while implementing #412; directory layout and plugin directories confirmed by source review of `src/session.rs` `data_dir_for`/`api_socket_path_for` and `src/plugin_paths.rs`): every running session of one remote user runs the user's installed plugins' hooks, and all sessions get the same `HERDR_PLUGIN_CONFIG_DIR` and `HERDR_PLUGIN_STATE_DIR` (keyed by plugin id only). `herdr plugin config-dir` prints the same directory whatever `HERDR_SESSION` or `--session` says; only a different `XDG_CONFIG_HOME` changes it. Pane ids repeat across sessions (`w1:p1` exists in each), so a pane id does not identify a session. Read a hook's session from `HERDR_SOCKET_PATH`: `<config>/herdr/herdr.sock` for the default session, `<config>/herdr/sessions/<name>/herdr.sock` for a named one. A server started with a `HERDR_SOCKET_PATH` override hands hooks that custom path, which names no session. `HERDR_SESSION` was correct in those hooks (the name in a named session, unset in the default one), but it comes from the server's environment and herdr keeps an inherited value unvalidated when a socket override is set, so treat the socket path as authoritative; herdr's own session resolution also lets `HERDR_SOCKET_PATH` win. The Heeler plugin's derivation and its shared vectors live in `plugin/src/session.js` and `plugin/test-vectors/notification-session-v1.json`.
- Default session name, herdr 0.9.3 (live `herdr session list --json` while implementing #419; source review of `src/session.rs` `normalize_name`, unchanged since named sessions arrived in 0.5.3): the default session is listed as `"name":"default"` with `"default":true`, and `--session default` selects it, so no named session is ever called `default`. `heeler://agent` links therefore read `session=default` as the default session, which a Host stores as a blank `sessionName`.
